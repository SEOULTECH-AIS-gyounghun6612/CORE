## 논의 대상

### 배치를 선언으로 어떻게 짓나

지금은 소비처가 자리를 코드로 조립. 선언으로 옮길 때 물음 넷.

| 물음 | 걸리는 것 |
|---|---|
| 배치를 무엇으로 적나 | 스플리터 트리라 중첩이 생김. 평탄한 목록으로는 못 적음 |
| 자리에 무엇이 앉나 | `표현 이름 -> 위젯` 등록표가 필요 |
| 고르기를 어떻게 잇나 | 자리끼리의 신호. 선언이 들지 코드가 배선할지 |
| 비율 · 최소 크기 | 사람이 끌어 바꾼 것을 기억할지, 선언이 늘 이길지 |

- `app.Run` 은 본문 위젯 하나만 받으므로 이 결정과 무관. 나중에 얹어도 안 흔들림

### 붙어 뜨는 창을 어떻게 두나

본문 배치 밖에 뜨는 것(작업 창 · 팝아웃)이 갈 곳이 없음.

- 후보 - 자리에 겹쳐 띄우기 · 별도 창 · 자리를 하나 더 열기
- 창이 본문과 같은 상태를 봐야 하므로 배선이 자리와 다름
- 표준으로 둘지, 소비처가 알아서 할지부터 정할 것

### main layout 과 일반 layout 을 어떻게 가르나

| | 무엇 | 지금 자리 |
|---|---|---|
| main | 제품의 화면 결정. 자리 이름을 듦 | 소비처 |
| 일반 | 계약 하나를 여러 위젯으로 미는 것 | `*/form/layout/` |

- 지금 판정 기준은 `소비처가 하나인가`. 약함 - 둘째가 생기면 뒤집힘
- 후보 기준 - `자리 이름을 아는가`. 아는 것은 제품 결정

### editor 를 범주로 들일까

LENS 의 `gui/windows/editor/` 가 도메인 0 이라 여기 올 수 있음. 계약은 도구 · 이력 · 잠금 · 조준.

- 캔버스 계약을 이미 여기가 듦. 편집기는 그 위에 서는 층
- 걸리는 것 - `Target` 이 `raster` · `paint` · `bbox` 를 이름으로 듦. 그 어휘가 일반적인가
- `handle/`(커서 <-> 값)이 여기 `form/` 과 겹쳐 읽힘. 들이면서 이름을 볼 것

### 값 위젯을 어떻게 고르나

`Config_form` 이 자료형별 if 사슬로 위젯을 고름. 자료형이 늘면 그 사슬을 고쳐야 함.

- 등록표로 뒤집으면 위젯이 자기를 등록하고 폼은 찾기만 함
- 지금은 사슬이 짧아 급하지 않음. `kind` 변형(`path` 등)이 늘면 그때
- 같이 정해지는 것 - `Value` 계약. 지금 상속하는 위젯이 0 이라 등록도 `isinstance`
  거르기도 못 함. 등록표를 세우면 상속시키고, 안 세우면 계약을 걷음
